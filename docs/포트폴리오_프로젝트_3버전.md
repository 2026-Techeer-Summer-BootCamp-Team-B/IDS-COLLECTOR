# 포트폴리오 프로젝트 소개 — 3가지 버전

세 버전 모두 "배경 → 문제 → 해결" 흐름으로 풀었고, 프로젝트명 옆에 담당 역할을 바로 붙였습니다. 마음에 드는 버전 골라주시면 다른 프로젝트(폰쉼, S.O.S 등)도 같은 톤으로 맞춰드리겠습니다.

## 버전 1. 스토리텔링형 (문단 서술, 헤더 최소화)

가장 자연스럽게 읽히는 방식입니다. 소제목 없이 문단으로 쭉 이어지고, 배경-문제-해결이 한 문단 안에서 자연스럽게 흘러갑니다. 채용 담당자가 죽 읽어 내려가는 걸 전제로 한 버전입니다.

### 쿠버네티스 기반 SIEM 로그 수집·상관분석 플랫폼 (SENTINEL-OPS)
**2026.06 – 2026.09 · 풀스택 개발**
사용 기술: Kafka, Kubernetes, OpenTelemetry, OpenSearch, ClickHouse, Redis, PostgreSQL, Docker, Falco, React, FastAPI(Python)

쿠버네티스 환경에서는 WAF·WAS·컨테이너 런타임(Falco)·K8s Audit 4개 계층에서 로그가 각각 발생합니다. 문제는 이 로그들을 계층별로 따로 들여다보면, 공격자가 여러 계층을 순서대로 넘나드는 연쇄적인 공격 흐름이 "4개의 무관한 해프닝"으로 파편화돼 보인다는 점이었습니다. 개별 이벤트 알람은 울리지만 보안 담당자 눈에는 흔한 스팸성 접근처럼 보이고, 그 사이 공격자는 이미 목적을 달성하고 빠져나가는 구조입니다. 이 문제를 풀기 위해 로그를 단일 파이프라인으로 수집하고 다차원 상관분석으로 하나의 공격 시나리오로 엮는 SIEM 대시보드를 풀스택으로 개발했습니다.

가장 먼저 부딪힌 문제는 4개 로그 소스가 포맷도 발생 위치도 심각도 기준도 전부 다르다는 점이었습니다. OpenTelemetry로 전송 규격을 통일해서 이 문제를 해결했고, 초당 수천 건 규모로 몰리는 로그를 유실 없이 받아내기 위해 Kafka를 무손실 버퍼로 뒀습니다. 그다음 문제는 "이 흩어진 로그를 어떻게 하나의 사건으로 엮을 것인가"였습니다. Redis 기반 threshold/sequence 상관분석 엔진을 만들어 109개 탐지 시나리오(MITRE ATT&CK 38종 매핑)를 실시간 평가하고, 서로 다른 로그 계층에 걸친 공격 체인을 단일 인시던트로 자동 연결했습니다. 저장 단계에서도 문제가 있었습니다. 검색·집계·트랜잭션 요구가 서로 다른데 저장소 하나로 다 감당하면 성능도 정합성도 떨어졌습니다. PostgreSQL(사건 상태 관리)·OpenSearch(원문 검색)·ClickHouse(집계 통계) 세 저장소를 목적별로 분리해 이 문제를 해결했고, 그 위에 React로 위젯 드래그앤드롭 배치·실시간 폴링·GeoIP 시각화를 갖춘 대시보드를 구현했습니다.

개발 과정에서 실제 장애로 이어질 뻔한 문제도 두 건 고쳤습니다. Kafka 컨슈머의 오프셋 커밋 순서를 잘못 설계해서, 처리에 실패한 이벤트가 재시도되지 않고 조용히 유실되는 문제를 발견했습니다. 원인은 라이브러리의 내부 fetch position이 메시지를 꺼내는 시점에 이미 전진해버려서 "커밋을 미루고 재시도"가 실제로는 작동하지 않았던 것이었고, 실패 시 같은 poll 안에서 동기 재시도 후 DLQ로 보내고서야 커밋하는 구조로 재설계해 유실을 막았습니다. 또 상관분석 엔진에서 여러 이벤트가 동시에 임계치를 넘길 때 각각 중복으로 발화하는 경쟁 조건도 발견해, Redis `SET NX` 원자적 클레임으로 정확히 하나만 발화하도록 고쳤습니다.

### 시흥시 외국인 행정 원클릭 플랫폼 (OneClick-Foreiner)
**2026.03 – 2026.06 · PM 및 안드로이드 개발**
사용 기술: Kotlin, Jetpack Compose, Firebase (Firestore / Auth), React, Vite

시흥시에 거주하는 외국인 주민들이 각종 행정·공공서비스 정보를 언어 장벽 없이 찾을 수 있도록 돕는 안드로이드 앱입니다. PM과 안드로이드 개발을 함께 맡아 UI/UX 설계부터 Firebase 연동까지 담당했습니다. Jetpack Compose로 화면을 구성하고 Firebase Authentication으로 로그인을, Firestore로 데이터 관리를 구현했습니다.

개발 중반에는 관리자용 웹 대시보드(React/Vite)와 모바일 앱이 같은 Firestore 인스턴스를 각자 다른 클라이언트에서 접근하다 보니 보안 규칙이 서로 충돌하는 문제가 발생했습니다. 이 문제를 원인부터 추적해서 해결한 경험이 있습니다.

## 버전 2. 구조화 프로즈형 (소제목으로 배경/문제/해결 명시)

한눈에 훑어보기 좋은 버전입니다. 각 기능 단위마다 짧은 소제목을 달아서, 채용 담당자가 빠르게 스캔하면서도 각 항목 안에서는 서사가 이어지도록 했습니다.

### 쿠버네티스 기반 SIEM 로그 수집·상관분석 플랫폼 (SENTINEL-OPS)
**2026.06 – 2026.09 · 풀스택 개발**
사용 기술: Kafka, Kubernetes, OpenTelemetry, OpenSearch, ClickHouse, Redis, PostgreSQL, Docker, Falco, React, FastAPI(Python)

쿠버네티스 환경에서 WAF·WAS·컨테이너 런타임(Falco)·K8s Audit 4개 계층의 로그가 계층별로 따로 관제되면서, 여러 계층을 넘나드는 연쇄적인 공격 흐름이 파편화되어 놓치는 문제를 해결하기 위해 만든 SIEM 대시보드입니다. 로그 수집·전송·상관분석·저장·시각화 전 영역을 풀스택으로 개발했습니다.

**흩어진 로그를 하나의 사건으로 — Redis 상관분석 엔진**
배경: 로그가 표준화되어 한곳에 모인 뒤에도, 실제 공격은 여러 계층을 순서대로 넘나들며 진행됐습니다.
문제: 로그를 계층별로 따로 보면 개별 알람은 울려도 전체 공격 흐름은 보이지 않아, 연쇄적인 침투를 놓칠 위험이 있었습니다.
해결: Redis 기반 threshold/sequence 상관분석 엔진으로 109개 탐지 시나리오(MITRE ATT&CK 38종 매핑)를 실시간 평가해, 서로 다른 로그 계층에 걸친 공격 체인을 단일 인시던트로 자동 연결했습니다.

**트러블슈팅 — Kafka 오프셋 커밋 순서 오류**
문제: 처리 실패한 이벤트를 "커밋 미루고 다음 poll에서 재시도"하도록 짰는데, aiokafka의 내부 fetch position이 커밋 여부와 무관하게 먼저 전진해버려 재시도가 일어나지 않고 조용히 유실되고 있었습니다.
해결: 같은 poll 안에서 동기 재시도 후 DLQ 처리·커밋하는 구조로 재설계했습니다.
결과: 실패 이벤트가 커밋 순서 때문에 조용히 사라지는 경로를 제거하고, 모든 실패를 DLQ로 추적 가능하게 만들었습니다.

**이기종 로그를 하나의 규격으로 — OpenTelemetry & Kafka**
배경: 프로젝트 초기에 WAF·WAS·Falco·K8s Audit 4개 로그 소스를 하나의 파이프라인에 모아야 했습니다.
문제: 4개 로그 소스는 포맷·발생 위치·심각도 기준이 전부 달라서, 그대로 모으면 상관분석 단계에서 매번 필드를 다시 맞춰야 했습니다.
해결: OpenTelemetry로 전송 규격을 통일하고, 초당 수천 건 규모로 몰리는 트래픽을 유실 없이 받기 위해 Kafka를 무손실 버퍼로 뒀습니다. OTel Collector의 routing connector가 `log.source` 태그를 기준으로 소스별 파이프라인을 자동 분기해 4개 원본 토픽(WAF/WAS/Falco/K8s Audit, 24시간 보관)으로 발행하고, 정규화가 끝난 이벤트는 `events.normalized` 토픽으로, 처리에 실패한 이벤트는 DLQ 토픽(7일 보관)으로 분리해 유실 없이 재처리할 수 있도록 구성했습니다.

**저장소 하나로는 부족했다 — 3중 저장 구조**
배경: 상관분석 결과와 원본 로그를 함께 다루면서, 검색·집계·트랜잭션이라는 서로 다른 워크로드가 동시에 필요했습니다.
문제: 검색·집계·트랜잭션 요구가 서로 다른 데이터를 저장소 하나에 몰면 성능도 정합성도 떨어졌습니다.
해결: PostgreSQL(사건 상태)·OpenSearch(원문 검색)·ClickHouse(집계 통계) 세 저장소를 목적별로 분리해 워크로드별 성능을 확보했습니다. OpenSearch는 Data Prepper가 원본 4개 토픽을 직접 구독해 일별 인덱스로 적재하고, ClickHouse는 정규화 토픽을 네이티브 Kafka Engine 테이블로 구독한 뒤 Materialized View로 분석 테이블에 반영하며, PostgreSQL은 Kafka를 직접 구독하지 않고 상관분석 엔진이 만든 인시던트 결과만 저장하도록 역할을 나눴습니다.

**트러블슈팅 — 상관분석 엔진 중복 발화 경쟁 조건**
문제: 여러 이벤트가 거의 동시에 threshold를 넘기면 각각 독립적으로 발화를 시도해, 같은 사건에 대해 인시던트가 중복 생성될 수 있었습니다.
해결: Redis `SET NX` 원자적 클레임으로 발화 권한을 하나만 갖도록 재설계했습니다.
결과: 동시성 상황에서도 하나의 사건이 하나의 인시던트로만 기록되도록 보장했습니다.

**보이지 않으면 소용없다 — React 대시보드**
배경: 파이프라인이 수집·분석한 데이터를 보안 담당자가 실제로 매일 들여다보고 판단에 써야 했습니다.
문제: 데이터를 실제로 활용하려면 보기 좋은 것만으로는 부족하고, 필요한 정보를 원하는 형태로 볼 수 있어야 했습니다.
해결: 위젯 드래그앤드롭 배치, 실시간 폴링, GeoIP 시각화를 갖춘 커스터마이징 가능한 대시보드를 구현했습니다.

## 버전 3. 타임라인형 (프로젝트 진행 흐름 순서로 서술)

"어떻게 만들어갔는가"를 시간 순서로 보여주는 버전입니다. 면접에서 "이 프로젝트 설명해주세요"라고 물었을 때 그대로 말해도 되는 흐름이라, 구술 스토리와 문서를 일치시키고 싶을 때 좋습니다.

### 쿠버네티스 기반 SIEM 로그 수집·상관분석 플랫폼 (SENTINEL-OPS)
**2026.06 – 2026.09 · 풀스택 개발**
사용 기술: Kafka, Kubernetes, OpenTelemetry, OpenSearch, ClickHouse, Redis, PostgreSQL, Docker, Falco, React, FastAPI(Python)

쿠버네티스 환경의 WAF·WAS·Falco·K8s Audit 4개 계층 로그가 각각 따로 관제되면서 연쇄적인 공격 흐름을 놓치는 문제를 해결하기 위해 시작한 프로젝트입니다. 기획부터 로그 수집 파이프라인, 상관분석 엔진, 저장 계층, 대시보드까지 풀스택으로 개발했습니다.

가장 먼저 손댄 건 수집 단계였습니다. 4개 소스의 포맷이 제각각이라 OpenTelemetry로 규격을 통일하고, 초당 수천 건 트래픽을 안전하게 받기 위해 Kafka를 무손실 버퍼로 세웠습니다. 이 위에 Redis 기반 threshold/sequence 상관분석 엔진을 얹어 109개 탐지 시나리오(MITRE ATT&CK 38종 매핑)를 실시간 평가하도록 만들었고, 서로 다른 계층에 걸친 공격 체인을 하나의 인시던트로 묶어내는 데까지 성공했습니다. 그다음엔 저장 구조를 정리했습니다. 검색·집계·트랜잭션 요구가 다른 데이터를 저장소 하나로 몰아 쓰다 보니 성능과 정합성 문제가 보였고, PostgreSQL·OpenSearch·ClickHouse로 목적에 맞게 분리했습니다. 마지막으로 이 모든 걸 사용자가 실제로 다룰 수 있도록 React 대시보드에 위젯 드래그앤드롭, 실시간 폴링, GeoIP 시각화를 붙였습니다.

운영에 가까워지면서 두 가지 문제를 실제로 겪었습니다. 하나는 Kafka 컨슈머 오프셋 커밋 순서 문제로, 처리 실패 이벤트가 재시도 없이 조용히 유실되고 있던 걸 발견해 동기 재시도 후 DLQ 커밋 구조로 재설계했습니다. 다른 하나는 상관분석 엔진의 중복 발화 경쟁 조건으로, 여러 이벤트가 동시에 임계치를 넘길 때 발생할 수 있는 문제를 Redis 원자적 클레임(`SET NX`)으로 막았습니다.
