# SENTINEL-OPS: 흩어진 로그 네 갈래를 하나의 공격 시나리오로 엮다

개인정보 유출이 빈번하게 일어나고 있다. 어느덧 유출된 개인정보의 수가 인류의 인구수를 뛰어넘었다는 이야기까지 나온다.

그렇다면 빅테크 보안이 계속 뚫리는 결정적 이유는 무엇일까. 세계 최고의 보안 인력과 최첨단 방화벽 시스템을 갖춘 기업들조차 왜 해커에게 매번 한 발 늦는 걸까. 이 질문의 답을 찾기 위해, 클라우드 네이티브의 핵심인 쿠버네티스(Kubernetes) 환경 내에서 수집되는 로그 데이터를 깊이 들여다보았다.

#### 보안에 실패하는 이유

각 단계에서 수집되는 로그들은 하나하나 따로 보면 이상이 없어 보이기도 한다. 바로 여기서 문제가 발생한다. 세계적인 기업들조차 보안에 실패하는 결정적인 이유는 결국 '공격의 흐름'과 '관제 시선'의 불일치에 있었다.

실제 해커들의 공격은 단 하나의 지점만 타격하지 않는다. 공격자는 시스템의 여러 레이어를 순서대로 교묘하게 넘나들며 침투한다.

원래 쿠버네티스 보안을 논할 때 흔히 이야기되는 계층은 Cloud - Cluster - Container - Code, 이른바 4C 모델이다. 처음 설계할 때도 이 4단계를 그대로 가져가려고 했다. 다만 Cloud 계층(클라우드 사업자 단의 IAM·감사 로그 등)은 실제로 수집하려면 클라우드 제공자 쪽 권한과 별도 연동이 필요했고, 우리가 쓸 수 있는 서버 자원과 개발 기간 안에서는 이 부분까지 온전히 구현하기가 현실적으로 어려웠다. 그래서 Cloud 대신, 실제 침투 흐름에서 더 앞단이자 우리가 직접 통제하고 로그를 뽑아낼 수 있는 WAS 계층을 넣어 4단계를 재구성했다. 이론적으로 완전한 4C 모델은 아니지만, 우리가 감당할 수 있는 환경 안에서 침투 흐름을 가장 잘 설명할 수 있는 조합을 택한 셈이다.

**실제 침투가 이루어지는 4단계 계층**

- **WAF** — 웹 방화벽 탐지 우회
- **WAS** — 웹 애플리케이션 취약점 공격
- **Falco** — 컨테이너 런타임 이상 행동 발생
- **K8s Audit** — 쿠버네티스 클러스터 권한 탈취 및 확장

그런데 문제는 기존의 보안 관제 체계다. 로그를 각 계층별로 독립적으로만 들여다보는 기존 관제 환경에서는 이 연쇄적인 공격 흐름이 '4개의 서로 무관한 해프닝'으로 파편화되어 버린다.

관제 화면에 개별 이벤트 알람은 울리지만, 보안 담당자 눈에는 그저 흔한 스팸성 접근처럼 보일 뿐이다. 나무만 보고 숲을 보지 못하는 사이에, 공격자는 이미 목적을 달성하고 유유히 빠져나간다.

#### 파편화된 흔적을 하나의 시나리오로: SENTINEL-OPS

이러한 치명적인 관제 사각지대를 해결하기 위해 탄생한 솔루션이 바로 SENTINEL-OPS다.

SENTINEL-OPS는 흩어져 있던 4개 계층(WAS · WAF · Falco · K8s Audit)의 로그를 단일 파이프라인으로 수집한다. 그리고 다음의 핵심 기준을 바탕으로 다차원 상관분석(Correlation Analysis)을 수행한다.

## 상관분석 엔진, 어떻게 "하나의 공격"으로 엮는가

시나리오 룰은 카테고리별(자격증명·방어 회피·정찰·횡적 이동·네트워크·RBAC·리소스 남용·워크로드)로 선언돼 있고, 엔진이 이 파일을 30초마다 다시 읽어 핫리로드한다. 룰은 크게 두 형태다.

- **threshold(횟수 기반)**: "같은 IP가 60초 안에 로그인 실패 5번 이상" 같은 조건이다. Redis에 카운터를 올리다가 임계치를 넘기면 발화한다.
- **sequence(순서 기반)**: "A라는 행동 다음에 B라는 행동이 이어질 때만" 같은 다단계 조건이다. Redis에 진행 상태를 저장해뒀다가 다음 단계가 정해진 시간 안에 오면 전진시키고, 마지막 단계까지 도달하면 발화한다.

지금 시점 기준으로 총 109개의 시나리오가 등록돼 있다. 이 중 56개는 단발 threshold, 23개는 횟수 조건이 있는 threshold, 30개는 다단계 sequence이며, sequence 중 20개는 서로 다른 로그 계층(WAF→Falco, K8s Audit→Falco 등)을 넘나드는 크로스모듈 체인이다. 이 룰들이 다루는 MITRE ATT&CK 기법은 38종이다.

가장 인상적인 예시는 5단계짜리 체인이다. 공개된 웹앱에 대한 CRITICAL 등급 공격 차단(WAF) → 같은 Pod에서 컨테이너 내부 셸 실행(Falco) → 서비스어카운트 토큰 파일 탈취(Falco) → 그 토큰으로 새 서비스어카운트 토큰 발급(K8s Audit) → 클러스터 롤바인딩 생성 시도(K8s Audit)까지, 웹 침투가 어떻게 클러스터 장악 시도로 이어지는지를 WAF → Falco → K8s Audit 세 계층에 걸쳐 하나의 인시던트로 묶어낸다.

이런 체인은 로그를 계층별로 따로 보는 관제 체계에서는 절대 하나로 안 엮이는, 상관분석이 있어야만 잡히는 유형의 공격이었다.

### 기술 선택, 그리고 그 이유

#### OpenTelemetry — 서로 다른 코드가 지키는 하나의 약속

공격받는 대상 서버와 탐지 시스템은 서로 다른 팀, 다른 코드로 개발된다. 로그 포맷을 탐지 시스템 방식에 맞춰 짜야 했다면, 대상 서버 코드가 바뀔 때마다 탐지 시스템도 같이 손봐야 하는 결합이 생긴다.

그래서 업계 표준 규격인 OpenTelemetry로 로그를 보내기로 약속하고, 탐지 시스템은 그 표준 규격만 받으면 되도록 만들었다. 대상 서버가 내부적으로 무엇을 하든 신경 쓸 필요가 없어진다.

#### Kafka — 무손실 버퍼, 그리고 세 갈래로 흐르는 데이터

SENTINEL-OPS는 서로 다른 로그 소스에서 예측할 수 없는 속도로, 많을 때는 초당 수천 건씩 로그가 쏟아진다. 이 로그는 하나라도 유실되면 안 되고, 게다가 이후 correlation-engine·OpenSearch·ClickHouse 세 곳에서 각각 다른 목적으로, 각각 다른 속도로 쓰여야 한다. 그래서 조금 무겁더라도 로그를 안전하게 보존할 수 있는 Kafka를 중간 버퍼로 두고, 이후 각 시스템이 자신에게 필요한 속도로 가져가도록 만들었다.

### 세 개의 저장소, 세 가지 역할

같은 로그라도 쓰이는 목적이 다르면 최적의 저장소도 다르다.

- **PostgreSQL**: 이미 차단한 IP를 또 차단 시도하거나, 분명히 종결 처리한 사건 기록이 사라지는 건 보안 관제에서 치명적이다. 그래서 사건의 상태와 조치 이력만큼은 ACID를 지원해 데이터 정합성이 보장되는 PostgreSQL에 따로 관리한다(`incidents` / `incident_events` / `audit_logs`).
- **OpenSearch**: 실제 보안 사고를 조사할 때는 "이 IP가 남긴 로그 전부 보여줘"처럼 조건으로 로그 원문을 자유롭게 검색해야 할 때가 많다. 그래서 검색에 특화된 OpenSearch를 따로 뒀고, 대시보드의 로그 검색 기능이 여기서 나온다.
- **ClickHouse**: 대시보드의 그래프와 차트, 즉 집계 작업은 통계 계산에 최적화된 저장소를 쓰는 게 훨씬 빠르다. 그래서 컬럼형 저장소인 ClickHouse를 통계·그래프 전용으로 따로 뒀다.

## 마무리

SENTINEL-OPS는 "로그 하나하나를 잘 보여주는 대시보드"가 아니라 "흩어진 흔적을 하나의 이야기로 엮는 파이프라인"을 목표로 만들었다.
