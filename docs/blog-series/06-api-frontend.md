# [SENTINEL-OPS 아키텍처 시리즈 ⑥] API와 프론트엔드: 흩어진 저장소를 하나의 화면으로

*지난 글까지 로그가 수집되고, 인증받고, Kafka를 거쳐 세 저장소에 나뉘어 쌓이는 과정을 다뤘다. 이번 글은 이 흩어진 데이터를 다시 하나의 대시보드로 모으는 마지막 구간이다.*

## 저장소는 셋인데, 화면은 하나여야 한다

지금까지의 구조를 정리하면 이렇다.

- OpenSearch: 원본 로그 검색용
- ClickHouse: 통계·집계용
- PostgreSQL: 상관분석 결과(인시던트)와 조치 이력용

문제는 사용자가 보는 대시보드 입장에서는 이 구분이 전혀 중요하지 않다는 점이다. "지금 우리 클러스터에서 무슨 일이 벌어지고 있는지"를 보려는 사람은 KPI 카드 하나, 그래프 하나를 볼 때마다 그 데이터가 어느 저장소에서 왔는지 신경 쓰고 싶어 하지 않는다. 손님이 레스토랑에서 "이 요리 재료가 냉장고 몇 번 칸에서 나왔어요"를 궁금해하지 않는 것과 같다. 그냥 맛있게 나오면 그만이다. 이 간극을 메우는 게 FastAPI로 만든 API 백엔드다. 주방과 홀 사이를 오가며 손님 주문을 처리하는 웨이터 역할이다.

## FastAPI란 무엇인가

FastAPI는 Python 타입 힌트를 기반으로 요청/응답 스키마를 자동 검증하고 문서화하는 비동기 웹 프레임워크다. Starlette(ASGI) 위에서 동작해 비동기 I/O를 네이티브로 지원하고, Pydantic으로 요청 바디·쿼리 파라미터를 선언하면 자동으로 유효성 검사와 OpenAPI(Swagger) 문서가 생성된다.

### 장점

**비동기 I/O 네이티브 지원.** OpenSearch·ClickHouse·PostgreSQL 세 곳을 조회하는 API 서버는 대부분의 시간을 네트워크 I/O 대기에 쓴다. 동기 방식 웨이터는 한 손님 주문을 넣고 주방에서 요리가 나올 때까지 그 자리에 가만히 서서 기다린다. 그동안 다른 손님은 손을 들어도 응대를 못 받는다. `async/await`를 쓰는 비동기 웨이터는 주문을 넣어두고 바로 다음 테이블로 이동해서 또 주문을 받는다. 요리가 완성되면 그때 가져다준다. 같은 인원으로 훨씬 많은 테이블을 돌 수 있는 셈이다.

**타입 힌트 기반 자동 검증·문서화.** 함수 시그니처에 타입을 선언하는 것만으로 요청 검증과 API 문서(Swagger UI)가 따라온다. 프론트엔드 개발자가 백엔드 코드를 안 봐도 API 스펙을 바로 확인할 수 있다.

**Python 생태계.** 정규화·상관분석 엔진도 Python(normalizer, correlation-engine)으로 짜여 있어서, 스키마 정의(Pydantic 모델)를 서비스 간에 재사용하기 좋다.

### 단점

**Python 자체의 실행 속도.** Go나 Rust 기반 프레임워크보다 CPU 바운드 연산에서는 느리다. 다만 이 프로젝트의 API 서버는 대부분 I/O 바운드(DB 조회 대기)라 이 단점의 영향이 크지 않다. 웨이터가 요리를 직접 만드는 게 아니라 나르기만 하는 거라, 웨이터 발이 조금 느려도 크게 티가 안 나는 것과 비슷하다.

**GIL(Global Interpreter Lock) 제약.** 진짜 멀티코어 병렬 연산이 필요한 작업(무거운 데이터 가공 등)은 별도 프로세스로 분리해야 한다.

### 우리 프로젝트에 필요했던 이유

세 저장소를 동시에 조회하는 요청(예: Overview 화면 초기 로딩)이 많은데, 동기 프레임워크였다면 세 조회를 순차로 기다리거나 스레드풀에 의존해야 했을 것이다. FastAPI의 비동기 지원 덕분에 여러 저장소 조회를 동시에(`asyncio.gather` 등으로) 실행해 전체 응답 시간을 단축할 수 있었다. 세 주방(OpenSearch·ClickHouse·PostgreSQL)에 동시에 주문을 넣고, 셋 다 완성되면 한 쟁반에 담아 내가는 방식이다. 순서대로 한 주방씩 들렀다 오는 것보다 훨씬 빠르다. 또한 normalizer·correlation-engine과 같은 언어(Python)를 쓰면서 NormalizedEvent 같은 스키마를 서비스 간에 개념적으로 맞춰가기도 수월했다.

### 다른 후보군과 비교

**Django(+ DRF)** 는 ORM, 관리자 페이지, 인증 등 배터리가 다 포함된 풀스택 프레임워크다. 기능이 풍부하지만 그만큼 무겁고, 기본적으로 동기 처리 모델(ASGI 지원이 추가됐지만 생태계 전체가 동기 중심으로 성숙해 있음)이라 I/O 바운드 워크로드에 최적은 아니었다.

**Node.js(Express/Nest.js)** 도 비동기 I/O에 강하다는 점은 비슷하지만, 백엔드 팀이 이미 Python 기반 데이터 처리 파이프라인(normalizer, correlation-engine)을 쓰고 있어서 언어를 통일하는 쪽을 택했다.

**Spring(Java)** 은 엔터프라이즈급 안정성과 생태계가 강점이지만, 상대적으로 무거운 러닝 커브와 빌드·배포 복잡도가 이 프로젝트 규모에는 과했다.

## FastAPI: 요청 성격에 따라 저장소를 나눠 조회

API 서버는 요청의 성격에 따라 세 저장소 중 알맞은 곳을 조회한다.

- 자유 검색(`/logs`, 키워드·레벨·소스 조건 조합): OpenSearch
- 통계·집계(`/stats/kpi`, `/stats/volume`, `/stats/levels`, `/stats/by-country` 등): ClickHouse
- 인시던트 상태·조치 이력(`/incidents`, 조사 진행 상태, IP 밴 등): PostgreSQL

프론트엔드 입장에서는 이 구분이 API 뒤로 완전히 숨겨진다. 대시보드는 그냥 필요한 엔드포인트를 호출할 뿐이고, "이 데이터가 원래 어느 저장소에 있었는가"는 API 서버만 알면 되는 정보다.

## 실시간성: WebSocket이냐 폴링이냐

### 개념

**폴링(Polling)**은 클라이언트가 일정 주기로 서버에 "새로운 게 있어?"라고 반복해서 물어보는 방식이다. **WebSocket**은 클라이언트-서버 간 커넥션을 한 번 맺어두고, 서버가 이벤트가 생길 때마다 그 커넥션으로 즉시 밀어주는(push) 양방향 통신이다.

폴링은 2초마다 친구에게 전화해서 "택배 왔어? 왔어? 왔어?"를 반복하는 사람이고, WebSocket은 "택배 오면 바로 문자 줘"라고 한 번 말해두고 기다리는 사람이다. 후자가 훨씬 우아해 보이지만, 전화선을 계속 붙잡고 있어야 한다는 건 그 나름의 비용이다.

### 각각의 장단점

폴링은 구현이 단순하고 기존 REST 인프라를 그대로 쓸 수 있다는 장점이 있지만, 주기를 짧게 잡으면 실제로 새 데이터가 없어도 요청이 계속 나가서 낭비고, 길게 잡으면 반영이 늦다.

WebSocket은 이벤트 발생 즉시 반영되고 불필요한 요청이 없다는 장점이 있지만, 커넥션을 유지하는 서버 자원 비용이 있고, 프록시·로드밸런서 설정이 폴링보다 까다롭다(3편에서 다룬 h2c 문제와 비슷한 성격의 함정이 있을 수 있다).

### 우리 프로젝트의 선택: 둘 다 쓰되 역할을 나눴다

SENTINEL-OPS는 화면 성격에 따라 두 방식을 나눠 쓴다. KPI 카드나 통계 그래프처럼 몇 초 단위로 갱신돼도 괜찮은 화면은 폴링을, 실시간 이벤트 티커나 공격 알림처럼 발생 즉시 반영되어야 하는 화면은 WebSocket(`/ws/events`, `/ws/incidents`)을 쓴다. 모든 걸 WebSocket으로 통일하지 않은 이유는, KPI·통계처럼 몇 초 지연이 문제되지 않는 데이터까지 상시 커넥션을 유지할 필요는 없다고 판단했기 때문이다. 택배야 조금 늦게 알아도 그만이지만, 도둑이 들었다는 소식은 바로 알아야 하니까.

## 트러블슈팅이자 개선 스토리: 폴링 주기를 사용자가 직접 설정하게 만들다

처음에는 실시간 폴링 주기가 코드에 2초(2000ms)로 고정되어 있었다(`LIVE_POLL_MS` 상수). Overview, WAS, Falco, K8s Audit 상세 화면과 LiveTicker가 전부 이 값을 그대로 가져다 썼다. 문제는 이 2초라는 값이 모든 상황에 맞는 정답이 아니라는 점이었다. 시연처럼 "지금 막 일으킨 공격이 화면에 바로 뜨는 걸 보여주고 싶은" 상황에서는 2초도 느리게 느껴졌고, 반대로 여러 브라우저 탭을 켜두고 오래 모니터링만 하는 상황에서는 2초마다 나가는 조회 요청이 백엔드에 불필요한 부하로 누적됐다. 성격 급한 사람과 느긋한 사람이 같은 시계를 봐야 하는데, 그 시계가 아무한테도 딱 맞지 않는 상황이었다.

고정값 하나로는 이 두 요구를 동시에 만족시킬 수 없다고 판단해서, 폴링 주기 자체를 관리자가 화면에서 직접 바꿀 수 있게 만들기로 했다.

### 구현: PollIntervalContext

`LIVE_POLL_MS`라는 고정 상수를 여러 훅이 직접 import하던 구조를, React Context로 옮겨서 전역 상태로 관리하도록 바꿨다.

```jsx
// PollIntervalContext.jsx
const STORAGE_KEY = "sentinelops_poll_interval_ms";

export function PollIntervalProvider({ children }) {
  const [pollMs, setPollMsState] = useState(loadInitial); // localStorage 우선, 없으면 기본값

  const setPollMs = useCallback((ms) => {
    setPollMsState(ms);
    window.localStorage.setItem(STORAGE_KEY, String(ms));
  }, []);

  return (
    <PollIntervalContext.Provider value={{ pollMs, setPollMs, defaultPollMs: LIVE_POLL_MS }}>
      {children}
    </PollIntervalContext.Provider>
  );
}
```

각 실시간 패널은 `usePollInterval()`이라는 훅으로 "지금 값"을 구독한다. 관리자가 Admin 화면에서 값을 바꾸면, 코드를 재배포하지 않아도 모든 실시간 패널이 즉시 새 간격으로 갱신된다. 벽시계를 하나만 바꿔 걸어도 건물 안의 모든 시계가 자동으로 맞춰지는 셈이다.

### 왜 프리셋 방식으로 한계를 뒀나

Admin 화면에는 임의의 숫자를 입력하는 대신 프리셋 버튼(0.5초 / 1초 / 2초 / 5초 / 10초 / 30초)을 뒀다.

```jsx
const POLL_INTERVAL_PRESETS = [
  { label: "0.5초", ms: 500 },
  { label: "1초", ms: 1000 },
  { label: "2초", ms: 2000 },
  { label: "5초", ms: 5000 },
  { label: "10초", ms: 10000 },
  { label: "30초", ms: 30000 },
];
```

하한을 500ms로 둔 이유는, 이보다 짧아지면 백엔드 집계 쿼리(ClickHouse 통계, OpenSearch 검색) 호출 빈도가 과도하게 늘어나 서버 부담이 커지기 때문이다. 상한을 30초로 둔 이유는, 그 이상으로 늘어나면 "실시간 대시보드"라는 제품 성격 자체가 옅어진다고 판단했기 때문이다. 아무리 여유로운 사람도 30초 넘게 걸리는 "실시간"은 실시간이라 부르기 민망하다. 이 범위 안에서 사용자가 상황에 맞게 고를 수 있게 하는 것으로 충분하다고 봤고, 임의 값 입력 UI는 지금은 만들지 않았다(Context의 `setPollMs` 자체는 임의의 ms 값을 받을 수 있어서, 필요해지면 숫자 입력 필드만 추가하면 된다).

### 값을 어디에 저장할지도 고민한 지점

이 설정을 백엔드 DB에 저장할지, 브라우저에만 저장할지도 판단이 필요했다. "화면 갱신 빈도"는 다른 관리 설정(탐지 룰 on/off, 데이터 보존 정책 등)과 달리 서버 상태라기보다 개인의 화면 사용 습관에 가깝다고 봐서, 지금은 `localStorage`에 저장해 브라우저별로 기억하도록 했다. 여러 관리자가 같은 값을 공유해야 할 필요가 생기면 `/settings` 같은 API로 옮기면 되는 구조로 열어뒀다.

### 응답 시간을 측정하는 지표도 함께 뒀다

폴링 주기를 조절할 수 있게 만든 것과 별개로, 실제로 로그가 얼마나 빨리 반영되고 있는지를 확인할 수 있는 지표도 API에 뒀다. `GET /stats/clock-skew`는 `event.ingested`(수집 시각)와 원본 이벤트의 `@timestamp`(발생 시각) 차이를 OpenSearch의 `attack-logs-*` 인덱스 기준으로 표본 추출해서 보여준다. 폴링 주기를 아무리 짧게 잡아도 그 앞단(배치 타임아웃, flush 주기 등 4편·5편에서 다룬 튜닝들)이 느리면 소용없기 때문에, 파이프라인 전체의 실제 지연을 항상 관찰할 수 있게 만든 지표다. 웨이터가 아무리 빨리 뛰어도 주방이 느리면 소용없는 것처럼, 진짜 병목이 어디인지 늘 확인할 수 있어야 한다.

## 시리즈를 마치며

정리하면 이 프로젝트는 표준화된 수집(OTel/OTLP) → 빠른 전송(gRPC) → mTLS로 인증된 관문(Traefik) → 안정적인 분배(Kafka) → 목적별 저장(OpenSearch/ClickHouse/PostgreSQL) → API 서빙(FastAPI)과 상황에 맞춘 실시간 반영(폴링 + WebSocket)으로 이어지는 파이프라인을 통해, 쿠버네티스 3계층 로그를 하나의 상관분석 대시보드로 통합하는 것을 목표로 만들었다.

각 단계마다 "왜 이 기술을 선택했는가"뿐 아니라 "왜 이 기본값을 골랐고, 왜 나중에 바꿨는가"까지 근거를 남기려 했다. h2c 오인식, 오프셋 커밋 순서, 배치·flush 타임아웃, 고정 폴링 주기처럼 문서만 봐서는 알기 어려운 문제들을 실제로 겪고 고치는 과정에서, 트래픽이 늘거나 저장소가 추가돼도 구조를 크게 흔들지 않고 확장할 수 있는 파이프라인에 조금 더 가까워졌다고 생각한다.
