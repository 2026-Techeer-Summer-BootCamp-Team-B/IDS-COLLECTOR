# [SENTINEL-OPS 아키텍처 시리즈 ③] 관문: Traefik과 mTLS

*지난 글에서는 gRPC로 로그를 빠르게 전송하는 이유를 다뤘다. 이번 글은 그 gRPC 트래픽이 클러스터 안으로 들어오기 전, 실제로 어떻게 인증받는지 다룬다.*

## Traefik이란 무엇인가

Traefik은 Go로 작성된 오픈소스 리버스 프록시이자 API 게이트웨이다. 외부에서 들어오는 요청을 도메인·경로 규칙에 따라 알맞은 백엔드 컨테이너로 라우팅하고, TLS 종료·인증·레이트 리밋 같은 공통 관심사(cross-cutting concern)를 애플리케이션 코드 밖에서 처리해주는 역할을 한다. 건물로 치면 로비의 안내 데스크다. 방문객이 몇 층 몇 호실을 가든 일단 로비를 거치고, 안내 데스크가 신분을 확인하고 방향을 알려준다. Docker/Kubernetes와 네이티브로 연동돼서, 컨테이너에 라벨을 붙이는 것만으로 라우팅 규칙을 선언할 수 있다는 게 특징이다.

SENTINEL-OPS에서는 이 Traefik이 단일 진입점 역할을 한다. 로그 인입 트래픽(otlp-grpc)과 대시보드 API 트래픽(platform-api)이 같은 로비를 거치되, 서로 다른 안내 규칙으로 완전히 분리되어 라우팅된다.

## 장점

**선언적 설정.** 별도 설정 파일 없이 Docker Compose 라벨만으로 라우터·미들웨어·TLS 옵션을 정의할 수 있다. 서비스를 추가하거나 라우팅 규칙을 바꿀 때 Traefik 자체를 재배포할 필요 없이 컨테이너 라벨만 바꾸면 된다. 안내 데스크 직원을 다시 교육할 필요 없이, 안내판 문구만 바꿔 붙이면 되는 셈이다.

**자동 서비스 디스커버리.** 컨테이너가 뜨고 내려가는 걸 Docker 소켓을 통해 자동으로 감지해서 라우팅 테이블을 갱신한다. 정적 설정 파일을 손으로 관리할 필요가 없다.

**ACME(Let's Encrypt) 내장 지원.** 인증서 발급·갱신을 Traefik이 알아서 처리한다.

**미들웨어 체인.** 인증, 헤더 조작, 리트라이, 서킷 브레이커 같은 기능을 미들웨어로 조합해서 라우터마다 다르게 적용할 수 있다. 안내 데스크 앞에 "신분증 확인 → 방문증 발급 → 층수 안내" 순서로 검문 단계를 쌓아둘 수 있는 셈이다.

## 단점

**Docker 라벨 문법이 장황해질 수 있다.** 라우터·서비스·미들웨어를 전부 라벨 문자열로 표현하다 보니, 규칙이 복잡해질수록 `docker-compose.yml`이 길어지고 오타에 취약해진다. mTLS의 clientAuth/CA 지정처럼 라벨로 표현 불가능한 옵션은 별도 파일(File Provider)로 빼야 해서, 설정이 두 곳으로 나뉘는 불편함이 있다. 라벨을 한 줄씩 늘려가다 보면 어느 순간 "내가 인프라를 짜고 있는 건지, 주문 마법서를 쓰고 있는 건지" 헷갈리는 순간이 온다.

**성능은 Nginx/Envoy 대비 열세일 수 있다.** Go 기반 동적 라우팅의 유연함을 얻는 대신, 극한의 처리량이 필요한 상황에서는 정적 설정 기반의 Nginx나 데이터 플레인에 특화된 Envoy보다 오버헤드가 있을 수 있다.

**HTTP/2·gRPC 프록시 설정이 까다롭다.** 뒤에서 다룰 h2c 이슈처럼, 백엔드와의 통신 프로토콜을 명시적으로 지정하지 않으면 예상치 못하게 실패할 수 있다.

## 처음엔 "토큰이면 되지 않을까" 생각했지만

로그·보안 데이터를 다루는 시스템인 만큼, 인증되지 않은 소스가 로그 파이프라인에 임의로 데이터를 주입하는 걸 막아야 한다는 건 처음부터 명확했다. 가장 단순한 방법은 공유 토큰(예: 헤더에 시크릿 값을 실어 보내고 일치 여부만 확인)이다. 실제로 대시보드 API 쪽(platform-api)은 이런 방식에 가까운 게이트웨이 시크릿 헤더 검증을 쓴다.

하지만 OTel 로그 인입 구간에는 이보다 한 단계 더 강한 방식을 적용했다. 바로 **mTLS(상호 TLS, Mutual TLS)** 다.

## mTLS란 무엇인가

일반적인 TLS(HTTPS)는 클럽 입구에서 경비원이 신분증을 확인하는 것과 비슷하다. 다만 확인은 한쪽 방향뿐이다. 손님(클라이언트)은 "여기가 진짜 그 클럽 맞는지"(서버 인증서) 확인하지만, 경비원은 손님이 누군지 딱히 안 물어본다. mTLS는 여기서 한 단계 더 나가서, 손님도 자신의 신분증(클라이언트 인증서)을 제시해야 하고 경비원이 그걸 검증해야만 입장이 허락된다. "서버가 클라이언트를 신뢰한다"는 방향의 신뢰 관계가 암호학적으로 보장된다는 점이 핵심이다.

### 장점

토큰 같은 공유 비밀(shared secret) 방식은 헤더 값 하나만 탈취하면 재사용할 수 있지만, mTLS는 개인키까지 함께 탈취해야 위장할 수 있어서 인증 강도 자체가 다르다. 회원권 카드 한 장 슬쩍하는 것과, 회원권 카드에 더해 그 사람 지문까지 훔쳐야 하는 것의 차이랄까. 또한 TLS 핸드셰이크 단계에서 인증이 끝나기 때문에, 애플리케이션 레벨 코드에 도달하기도 전에 인가되지 않은 연결을 차단할 수 있다.

### 단점

인증서 발급·배포·회전(rotation) 관리 비용이 토큰보다 훨씬 크다. CA를 직접 운영해야 하고, 클라이언트 인증서가 만료되거나 CA가 바뀌면 양쪽을 동시에 갱신해야 한다. 소규모 프로젝트에는 과할 수 있는 복잡도다.

### 우리 프로젝트에 필요했던 이유

SENTINEL-OPS는 로그 인입 경로가 "여기로 들어오는 데이터는 반드시 신뢰할 수 있는 소스여야 한다"는 요구가 특히 강한 구간이다. 이 경로로 임의의 데이터가 주입되면 상관분석 엔진이 잘못된 인시던트를 만들어낼 수 있고, 반대로 진짜 공격 로그가 섞여서 묻힐 수도 있다. 대시보드 API처럼 사람이 세션 토큰으로 로그인하는 구간과 달리, 이 구간은 "서버 대 서버"로 지속적으로 신뢰가 유지돼야 하는 구간이라 mTLS의 강한 상호 인증이 더 맞다고 판단했다.

### 다른 후보군과 비교

**공유 토큰(Bearer/API Key)** 은 구현이 가장 간단하지만, 헤더 하나만 노출되면 그대로 위장 가능하다는 게 로그 인입 경로에는 부담이었다.

**mTLS 없이 IP 화이트리스트만 쓰는 방법**도 고려할 수 있지만, Target 서버의 IP가 바뀔 수 있고(클라우드 환경 특성상), IP 스푸핑 방어력도 인증서 기반 인증보다 약하다.

**OAuth2/JWT 기반 서비스 인증**은 사람 사용자 인증에는 적합하지만, 토큰 발급·갱신 흐름을 서버 대 서버 스트리밍 구간에 얹으면 오히려 복잡도만 늘어난다고 판단했다.

결국 인증서 기반의 강한 상호 신뢰가 필요하고, 이미 TLS 인프라(Let's Encrypt)를 쓰고 있던 상황이라 mTLS로 확장하는 비용이 상대적으로 낮았던 점도 고려했다.

## 실제 구성

```yaml
labels:
  - "traefik.http.routers.otlp-grpc.entrypoints=otlp-grpc"
  - "traefik.http.routers.otlp-grpc.rule=Host(`35-216-79-173.sslip.io`)"
  - "traefik.http.services.otlp-grpc.loadbalancer.server.scheme=h2c"
  - "traefik.http.routers.otlp-grpc.tls.certresolver=letsencrypt"
  - "traefik.http.routers.otlp-grpc.tls.options=otlp-mtls@file"
```

`tls.options=otlp-mtls@file`이 핵심이다. Traefik의 Docker 라벨 방식으로는 클라이언트 인증서 검증(clientAuth)이나 CA 파일 지정을 표현할 수 없어서, 이 옵션은 별도의 파일 기반 설정(`proxy/traefik/dynamic/tls-options.yml`)에 정의해두고 라벨에서는 참조만 한다. Target 서버 쪽 otel-collector exporter는 이미 클라이언트 인증서를 붙여서 요청을 보내고, Traefik은 이 인증서가 우리가 발급한 CA로 서명됐는지 검증한 뒤에만 요청을 통과시킨다.

## 트러블슈팅: h2c 프리페이스 오인식

이 구간을 만들면서 실제로 겪은 문제가 하나 있다. gRPC는 평문 통신을 할 때 h2c(HTTP/2 Cleartext)라는 방식을 쓰는데, 초기 설정에서는 Traefik이 이 gRPC 요청의 h2c 프리페이스(연결 시작 시 주고받는 초기 바이트열)를 일반 HTTP/1.1 요청으로 잘못 인식해서 요청이 깨지는 문제가 있었다.

원인은 Traefik이 백엔드 서비스로 요청을 넘길 때 어떤 프로토콜로 통신할지 스킴(scheme)을 명시하지 않으면 기본값을 HTTP/1.1로 가정한다는 데 있었다. gRPC 클라이언트가 h2c 프리페이스를 보내도 Traefik이 이걸 이해하지 못하고 일반 HTTP 요청처럼 처리하려다 실패하는 것이었다. 비유하면 택배 기사가 문 앞에서 특수 암호("h2c입니다")로 인사를 건넸는데, 경비실이 그걸 알아듣지 못하고 "그런 사람 안 계신데요" 하며 돌려보낸 셈이다. 증상만 보면 "gRPC 연결이 이유 없이 끊긴다"처럼 보여서, 처음엔 mTLS 인증서 문제인지 네트워크 문제인지부터 하나씩 배제해가며 원인을 좁혀야 했다. 밤늦게 Traefik 대시보드를 노려보며 "인증서는 멀쩡한데 왜 안 되지"를 되뇌던 시간이었다.

해결은 Traefik v3에서 백엔드 서비스의 스킴을 명시적으로 `h2c`로 지정하는 것이었다.

```yaml
- "traefik.http.services.otlp-grpc.loadbalancer.server.scheme=h2c"
```

이 한 줄로 Traefik이 백엔드(Collector)와 통신할 때 처음부터 h2c 프로토콜로 다루도록 강제해서 문제를 해결했다. 경비실 매뉴얼에 "h2c라고 인사하는 손님은 그냥 통과시켜라"는 한 줄을 추가한 셈이다. 인프라 설정 하나가 애플리케이션 레벨에서는 전혀 보이지 않는 원인으로 전체 로그 인입을 막을 수 있다는 걸 실감한 사례였다.
