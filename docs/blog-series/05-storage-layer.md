# [SENTINEL-OPS 아키텍처 시리즈 ⑤] 저장 계층: 세 저장소, 세 가지 역할

*지난 글에서는 Kafka를 중간 버퍼로 둔 이유를 다뤘다. 이번 글은 Kafka 뒤에서 실제로 데이터를 받는 세 저장소, OpenSearch·ClickHouse·PostgreSQL 이야기다.*

## 저장소를 하나로 통일하지 않은 이유

가끔 이런 질문을 받는다. "그냥 저장소 하나로 다 하면 안 돼요? 어차피 다 로그잖아요." 마음은 이해한다. 관리할 게 하나면 인프라 문서도 짧아지고, 배울 것도 줄고, 새벽에 장애 알림이 울릴 확률도 3분의 1이 된다.

그런데 이건 마치 한 사람한테 "너 요리도 잘하고 회계도 잘하고 소송도 잘 다루니까 우리 식당 요리사 겸 세무사 겸 변호사 해줘"라고 하는 것과 비슷하다. 각각 다 할 수는 있어도, 어느 하나도 제대로는 못 한다. 검색에 특화된 저장소 하나로 통계 집계까지 다 시키면 집계 쿼리가 느려지고, 집계에 특화된 저장소로 자유 검색까지 시키면 검색이 굼떠진다. 게다가 사건 상태처럼 "정확히 지금 이 순간의 진실"이 중요한 데이터를 검색·집계 저장소에 같이 두면, "방금 종결 처리한 사건이 인덱스 리프레시 타이밍에 따라 잠깐 다시 열린 것처럼 보이는" 정합성 문제까지 감수해야 한다. 담당자가 종결 버튼을 눌렀는데 화면에는 아직 "진행 중"이라고 뜬다면, 그건 버그가 아니라 순전히 이 저장소의 특성 때문에 벌어지는 일인데도 사용자 입장에서는 그냥 "왜 안 되지"로 느껴진다.

그래서 SENTINEL-OPS는 목적이 다른 세 저장소를 뒀다. 다만 이 셋은 "Kafka가 사이좋게 3등분해서 나눠주는 3개의 싱크"가 아니다. 저장소마다 Kafka를 소비하는 방식 자체가 다르고, 심지어 저장소마다 성격도 완전히 다르다. 하나씩 뜯어보자.

## OpenSearch: 원본 그대로의 포렌식 사본

### 개념

검색엔진이 빠른 이유를 이해하려면 "역색인(inverted index)"이라는 개념부터 짚어야 한다. 비유하자면 책 맨 뒤에 붙어 있는 "찾아보기" 페이지와 똑같다. 책을 처음부터 끝까지 넘겨가며 특정 단어를 찾는 대신("정색인" 방식), 찾아보기에서 그 단어를 먼저 찾고 "이 단어는 45쪽, 128쪽, 302쪽에 나옵니다"라고 바로 알려주는 방식이다. OpenSearch는 이 찾아보기를 모든 단어에 대해 미리 만들어두는 검색·분석 엔진이다. Elasticsearch에서 갈라져 나온(포크된) 오픈소스 프로젝트로, 기능적으로는 사실상 쌍둥이다.

### 장점

자유로운 조건 검색(키워드, 범위, 와일드카드 조합)이 압도적으로 빠르다. "IP가 이걸로 시작하고, 5xx 에러이고, 지난 3일 안에 발생한 것" 같은 복합 조건도 밀리초 단위로 응답한다. 스키마도 유연해서(schema-on-write지만 dynamic mapping 지원) 로그 소스마다 필드가 조금씩 다르더라도 웬만하면 알아서 받아준다. Kibana/OpenSearch Dashboards 같은 시각화 생태계도 탄탄하다.

### 단점

찾아보기를 만드는 건 공짜가 아니다. 문서를 하나 쓸 때마다 그 안의 모든 단어에 대해 찾아보기 항목을 갱신해야 하니, 쓰기 비용이 상대적으로 크다. 그리고 집계·통계 쿼리(예: "이번 주 시간대별 공격 건수를 다 더해서 그래프로 그려줘")는 컬럼 지향 OLAP 엔진보다 확실히 느리다. 찾아보기는 "이 단어가 어디 있어?"를 묻는 데는 최강이지만, "전체 문서를 한 바퀴 돌면서 숫자 하나로 요약해줘"는 원래 하는 일이 아니기 때문이다. 인덱스 단위로 리소스도 꽤 잡아먹어서, 인덱스 관리(보존 정책, 샤드 수)를 소홀히 하면 디스크와 힙 메모리가 생각보다 빨리 바닥난다. 이건 나중에 다룰 3등급 보존 정책 이야기와도 이어진다.

### 실제 구현

OpenSearch Data Prepper라는 별도 파이프라인 도구로 `events.was` / `events.waf` / `events.falco` / `events.audit`, 즉 소스별 원본 토픽 4개를 그대로 읽어서 일 단위 인덱스(`otel-logs-raw-YYYY.MM.DD`)에 적재한다.

```yaml
otel-logs-raw-pipeline:
  source:
    kafka:
      bootstrap_servers: ["kafka:9092"]
      topics:
        - name: "events.was"
          group_id: "opensearch-raw-consumer-group"
        # ...waf, falco, audit도 동일
  sink:
    - opensearch:
        index: "otel-logs-raw-%{yyyy.MM.dd}"
```

여기서 중요한 건 이 데이터가 **정규화를 거치지 않은 원본 그 자체**라는 점이다. 정규화 로직이 버그가 있거나 파서가 바뀌어도 이 원본 사본은 영향을 받지 않는다. 말하자면 "혹시 몰라서 남겨두는 CCTV 원본 영상"에 가깝다. 나중에 편집본(정규화된 데이터)에 문제가 생겨도, 원본만 있으면 언제든 다시 확인할 수 있다. "이 IP가 남긴 로그 전부 보여줘"처럼 조건으로 자유롭게 검색해야 할 때 이 역할을 맡는다.

### 다른 후보군과 비교

**Elasticsearch**는 OpenSearch의 원조 격으로 기능은 거의 동일하다. 다만 라이선스 정책이 SSPL로 바뀌면서(오픈소스 진영에서는 이 사건이 한동안 뜨거운 감자였다) 완전한 오픈소스 라이선스(Apache 2.0)를 유지하는 OpenSearch 쪽을 택했다.

**Grafana Loki**는 "라벨만 인덱싱하고 로그 본문은 인덱싱하지 않는" 경량 로그 저장소로, 찾아보기를 아예 안 만들다시피 해서 운영 비용이 낮다는 장점이 있다. 대신 라벨로 범위를 좁힌 다음 본문을 처음부터 grep하듯 훑는 방식이라, "본문 어디에든 이 IP가 있으면 찾아줘" 같은 자유 전문 검색에는 역색인 기반 엔진만큼 유리하지 않다. 보안 조사는 "이런 조건으로 찾아보고 싶다"는 게 매번 예상 밖으로 튀는 경우가 많아서, 다소 무겁더라도 역색인 기반을 택했다.

## ClickHouse: 정규화된 이벤트를 직접 소비하는 컬럼 저장소

### 개념

일반적인 데이터베이스(행 지향, row-oriented)는 데이터를 "한 사람의 정보를 통째로 한 줄에 담아 순서대로 쌓아두는 카드 상자"처럼 저장한다. 이름, 나이, 주소, 전화번호가 한 카드에 다 붙어 있는 식이다. 반면 ClickHouse 같은 컬럼 지향(column-oriented) DB는 "이름만 모아놓은 서랍, 나이만 모아놓은 서랍, 주소만 모아놓은 서랍"처럼 항목별로 따로 쌓아둔다.

이게 왜 유리하냐면, "전체 사용자의 평균 나이"를 구할 때 행 지향 방식은 카드 상자를 전부 열어서 이름도 보고 주소도 보고 전화번호도 보면서 나이만 골라내야 한다. 컬럼 지향은 그냥 "나이 서랍"만 열면 끝이다. 필요 없는 데이터는 아예 쳐다보지도 않는다. 그래서 "전체 행 중 일부 컬럼만 훑어서 집계"하는 연산이 압도적으로 빠르다.

### 장점

대용량 데이터에 대한 집계·통계 쿼리(GROUP BY, 카운트, 시간대별 추이)가 매우 빠르다. 컬럼별로 같은 종류의 값이 몰려 있다 보니 압축률도 좋아서(예: `event_module` 컬럼은 "was", "waf", "falco", "audit" 몇 가지 값만 반복되니 어마어마하게 잘 눌린다), 같은 데이터량이라도 디스크 사용량이 적다. 게다가 Kafka 엔진 테이블이라는 기능 덕분에 Kafka Connect 같은 외부 커넥터 없이도 ClickHouse가 스스로 Kafka 토픽을 구독해서 받아먹는다. 밥을 차려주지 않아도 알아서 냉장고 열어서 먹는 셈이다.

### 단점

대신 행 하나를 콕 집어서 고치는 갱신(UPDATE)이나 트랜잭션에는 영 소질이 없다(원래 append-only, 즉 "쌓기만 하고 잘 안 고치는" 워크로드에 맞춰 태어난 엔진이다). "이 서랍, 저 서랍, 그 서랍을 각각 다 열어서 특정 사람 한 명 찾기" 같은 포인트 조회(point lookup)도 검색엔진이나 RDB보다 느리다. 잘하는 일과 못하는 일이 극단적으로 갈리는 도구다.

### 실제 구현

```sql
CREATE TABLE normalized_events_queue (raw String)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = 'kafka:9092',
    kafka_topic_list = 'events.normalized',
    kafka_group_name = 'clickhouse-normalized-consumer-group',
    kafka_format = 'JSONAsString';

CREATE TABLE security_events_analytics (...)
ENGINE = MergeTree
PARTITION BY toDate(timestamp)
ORDER BY (timestamp, event_module)
TTL timestamp + INTERVAL 14 DAY;

CREATE MATERIALIZED VIEW security_events_analytics_mv TO security_events_analytics AS
SELECT ... FROM normalized_events_queue;
```

Kafka 엔진 테이블(`normalized_events_queue`)이 메시지를 받으면, Materialized View라는 게 중간에서 계속 지켜보고 있다가 JSON 문자열에서 타입 있는 컬럼(날짜, 문자열, 숫자 등)을 뽑아서 실제 분석용 테이블(`security_events_analytics`)로 옮겨 넣는다. 일종의 자동 분류 로봇이 컨베이어 벨트 옆에 서서 상자를 열어보고 알맞은 서랍에 넣어주는 그림이다. 원본이 아니라 정규화된 이벤트(`events.normalized`)를 소비하는 이유는, 통계·집계는 필드가 이미 통일된 형태여야 계산이 간단해지기 때문이다. WAS는 `src_ip`, Falco는 `source.ip`, 이런 식으로 필드명이 제각각이면 집계 쿼리 하나 짜는 데도 소스별 분기를 다 넣어야 해서 배보다 배꼽이 커진다.

### 다른 후보군과 비교

**TimescaleDB**는 PostgreSQL 확장이라 이미 쓰고 있는 PostgreSQL 생태계와 궁합이 좋다는 장점이 있다. 다만 근본적으로 행 지향 엔진 위에 시계열 최적화를 얹은 구조라, 순수 컬럼 지향 엔진만큼의 집계 성능은 기대하기 어렵다. 카드 상자에 색인표를 하나 더 붙여준 정도지, 서랍장으로 통째로 바꾼 건 아니라는 느낌이다.

**Apache Druid**는 실시간 집계·서브초 쿼리에 강한 컬럼 지향 엔진으로 ClickHouse와 자주 비교된다. 다만 운영 구성 요소(코디네이터, 오버로드, 히스토리컬 등 역할이 프로세스별로 쪼개져 있다)가 많아서, 사람도 서비스도 하나뿐인 단일 VM 환경에서 운영하기엔 ClickHouse보다 부담이 크다.

**BigQuery** 같은 완전관리형 서비스는 운영 부담이 없지만 특정 클라우드에 종속되고 쿼리 과금 구조라, 자체 호스팅 원칙과 맞지 않았다(그리고 학생 프로젝트 예산으로 쿼리 하나하나에 요금이 매겨지는 걸 지켜보는 건 심장에 좋지 않다).

## PostgreSQL: 로그 사본이 아니라 "관계"를 저장하는 곳

### 개념

PostgreSQL은 ACID 트랜잭션을 완전히 지원하는 오픈소스 관계형 데이터베이스다. ACID가 뭔지 은행 계좌 이체로 비유하면 이해가 쉽다. 내 계좌에서 10만 원이 빠져나갔는데 상대방 계좌에는 안 들어갔다면? 그건 재앙이다. ACID는 "빠져나가는 것과 들어가는 것이 항상 같이 성공하거나 같이 실패한다"는 걸 보장하는 성질이다. PostgreSQL은 이걸 완벽하게 지킨다.

여기서 처음 설계와 달라진 부분이 있다. PostgreSQL은 Kafka에서 로그 데이터를 직접 받는 세 번째 사본이 아니다. 대신 별도의 correlation-engine 서비스가 `events.normalized`를 소비해서 WAS·Falco·K8s Audit 세 계층의 이벤트를 서로 엮어낸 **상관분석 결과**(`incidents`, `incident_events`)와 조치 이력(`audit_logs`)만 저장한다. 로그 원문 수백만 건이 아니라, "그 로그들을 엮어서 만든 결론"만 여기 들어간다는 뜻이다.

### 장점

ACID를 보장하는 관계형 DB라 "이미 차단한 IP를 또 차단 시도한다"거나 "종결 처리한 사건 기록이 사라진다"처럼 정합성이 깨지면 안 되는 데이터를 안전하게 다룰 수 있다. 조인 연산과 외래키 제약, 트랜잭션 격리 수준을 세밀하게 통제할 수 있다는 것도 장점이다. 인시던트 하나에 이벤트 여러 개가 딸려 있고, 그 이벤트 하나하나에 조치 이력이 또 딸려 있는 구조(부모-자식-손자 관계)는 관계형 DB가 원래 잘하는 일이다.

### 단점

대용량 로그 원문을 그대로 저장하고 자유 검색까지 감당하기에는 적합하지 않다(그래서 그 역할을 OpenSearch에 분리했다). 수평 확장(샤딩)이 검색엔진이나 NoSQL만큼 자연스럽지 않아서, 트래픽이 아주 커지면 별도 확장 전략(읽기 복제본, 파티셔닝)이 필요하다.

### 실제 구현

OpenSearch와 ClickHouse가 각각 검색과 집계에 최적화된 대신 트랜잭션 처리에는 약한데, 그 빈틈을 PostgreSQL이 메운다. 로그 원본을 검색·집계 저장소에 흩어두더라도, "이 Falco 이벤트가 어떤 WAS 요청·어떤 K8s API 호출과 연결되는가"라는 관계 데이터는 트랜잭션이 보장되는 PostgreSQL에 두는 것이 안전하다고 판단했다. 비유하면 OpenSearch와 ClickHouse는 "사건 현장 사진 수만 장"을 보관하는 창고고, PostgreSQL은 "그 사진들을 보고 형사가 정리한 수사 결과 보고서"를 보관하는 금고다. 사진이야 좀 흐트러져 있어도 되지만, 보고서는 한 글자도 틀리면 안 된다.

### 다른 후보군과 비교

**MySQL**도 비슷한 ACID 관계형 DB지만, PostgreSQL이 JSON/JSONB 타입, 배열 타입, 풍부한 인덱스 종류(GIN 등) 등 이 프로젝트가 다루는 반정형 메타데이터(상관분석 결과에 딸린 가변적인 컨텍스트 필드)를 표현하기에 더 유리했다.

**MongoDB** 같은 문서형 DB는 스키마 유연성은 좋지만, 인시던트-이벤트-조치이력처럼 명확한 관계와 트랜잭션 정합성이 중요한 데이터에는 관계형 DB의 조인·외래키·트랜잭션이 더 안전한 선택이라고 판단했다. 유연함이 항상 미덕은 아니다. 가끔은 규칙이 빡빡한 게 오히려 마음이 편하다.

## 트러블슈팅: Data Prepper flush_timeout — 저볼륨 구간의 지연

OpenSearch Data Prepper는 문서를 모아뒀다가 일정 조건(개수 또는 시간)이 차면 한 번에 색인하는 배치 방식으로 동작한다. `flush_timeout` 기본값은 60000ms(1분)다. 트래픽이 많으면 배치가 개수 기준으로 금방 차서 문제가 안 되지만, 데모나 테스트처럼 이벤트가 뜨문뜨문 오는 저볼륨 상황에서는 이 1분이 그대로 "화면 반영 지연"의 원인이 됐다. 공격 로그 하나를 일부러 만들어놓고 화면 앞에서 새로고침을 연타하며 1분을 기다려본 사람이라면 이게 얼마나 애타는 시간인지 안다.

이 값을 500ms까지 낮췄다. 트래픽이 적을 때는 거의 실시간에 가깝게 색인되고, 트래픽이 많을 때는 어차피 배치 크기(bulk_size) 기준으로 더 일찍 플러시되므로 이 조정의 영향을 받지 않는다. 즉 "저볼륨일 때만 체감되던 지연"을 정확히 겨냥해서 줄인 튜닝이었다.

## 트러블슈팅: normalizer의 오프셋 커밋 순서 문제

`events.normalized`는 normalizer라는 서비스가 원본 토픽들을 소비해서 만들어낸다(`aiokafka` 사용, `enable_auto_commit=False`로 오프셋을 직접 관리). 이 정규화 과정에서 실제로 겪은 유실 문제가 하나 있다.

처음에는 "처리 실패한 메시지는 커밋을 미루고 다음 poll에서 재시도한다"는 방식으로 짰다. 얼핏 합리적으로 들리는 계획이었다. 그런데 `aiokafka`의 `async for` 이터레이터는 메시지를 꺼내주는 시점에 내부 fetch position을 이미 전진시켜버린다. 즉 커밋 없이 다음 메시지로 넘어가도(continue), 그 다음 메시지가 성공해서 커밋이 호출되는 순간 실패했던 메시지의 오프셋까지 통째로 확정돼버려서, "다음 poll에서 재시도"가 실제로는 일어나지 않고 조용히 유실되고 있었다. 재시도하려고 미뤄둔 숙제가 알고 보니 이미 "다 했음"으로 체크돼 있던 셈이다.

지금은 실패를 발견한 그 자리에서 정해진 횟수만큼 동기적으로 재시도하고, 그래도 실패하면 `events.dlq`로 보낸 다음에야 오프셋을 커밋하는 구조로 바꿔서 이 유실을 막았다.
