# [SENTINEL-OPS 아키텍처 시리즈 ④] 메시지 브로커: Elasticsearch 대신 Kafka를 택한 이유

*지난 글에서는 mTLS로 인증된 로그가 Traefik을 거쳐 Collector에 도달하는 과정을 다뤘다. 이번 글은 Collector 뒤에서 데이터를 받는 첫 관문, Kafka다.*

(참고로 이 이름은 소설가 프란츠 카프카와는 관계가 없다. 다만 설정을 처음 붙잡았을 때의 막막함은 어딘가 『성』스러운 구석이 있었다는 건 인정한다.)

## Kafka란 무엇인가

Apache Kafka는 분산 이벤트 스트리밍 플랫폼이다. 메시지를 "토픽"이라는 단위로 발행하고, 여러 consumer가 각자의 속도로 그 토픽을 구독(subscribe)해서 읽어가는 pub/sub 구조가 핵심이다. 우체국 사서함이라고 생각하면 쉽다. 편지(메시지)를 사서함(토픽)에 넣어두면, 그 사서함 열쇠를 가진 사람(consumer)이 각자 편한 시간에 와서 확인한다. 일반적인 메시지 큐(예: RabbitMQ)와 다른 점은, 편지를 한 번 읽었다고 사서함에서 바로 없애지 않는다는 점이다. 보존 기간 동안 그대로 놔둔다. 그래서 같은 사서함을 여러 사람이 독립적으로, 심지어 옛날 편지까지 처음부터 다시 읽을 수도 있다.

## 검색엔진에 바로 색인하는 구성도 고려했다

가장 단순한 구성은 Collector가 받은 로그를 곧바로 OpenSearch(Elasticsearch 계열)에 색인하는 것이다. 저장소가 하나 줄어드니 구조도 단순해진다. 우체국 사서함 없이 그냥 우편배달부가 집집마다 바로바로 배달하는 셈이다. 평소엔 문제없다. 문제는 명절이다.

## 장점

**백프레셔 흡수.** 로그는 항상 일정한 속도로 오지 않는다. 공격이 몰리는 순간, 혹은 여러 소스가 동시에 트래픽 스파이크를 겪는 순간에는 평소보다 훨씬 많은 로그가 한꺼번에 쏟아진다. 명절 택배 대란 때 배달원이 아무리 발버둥쳐도 물량을 못 따라가는 것과 같다. Kafka를 앞단 버퍼로 두면 "수집 속도"와 "저장 속도"를 분리(decouple)할 수 있다. 뒷단 저장소가 잠시 느려지거나 점검 중이어도, 로그는 일단 Kafka 토픽(사서함)에 안전하게 쌓이고 저장소가 정상화되면 밀린 만큼 이어서 처리한다.

**1대N 팬아웃.** 검색엔진은 검색·색인에 특화된 저장소일 뿐, 여러 소비자에게 같은 데이터를 나눠주는 용도로 설계되지 않았다. Kafka는 하나의 토픽을 여러 컨슈머 그룹이 각자의 속도와 방식으로 독립적으로 읽어갈 수 있게 해준다. 사서함 하나를 세 개의 다른 부서가 각자 열쇠를 갖고 독립적으로 확인하러 오는 셈이다. 한쪽 소비자가 느려지거나 잠시 멈춰도 다른 소비자에게 영향을 주지 않는다.

**재처리 가능성.** Kafka는 메시지를 즉시 지우지 않고 일정 기간 보존한다. 상관분석 로직을 수정하거나, 특정 저장소에 장애가 나서 데이터가 유실됐을 때도 토픽에 남아 있는 메시지를 처음부터 다시 흘려보내 재처리할 수 있다. 로그를 검색엔진에 한 번 색인해버리면 이런 재처리가 훨씬 번거로워진다. "아, 그때 그 로직 잘못 짰던 거 다시 계산하고 싶은데" 싶을 때 사서함에 편지가 아직 남아있다는 건 꽤 든든한 일이다.

**높은 처리량.** 순차 디스크 쓰기(append-only log) 구조 덕분에 초당 수십만 건 단위의 메시지도 처리할 수 있는 설계다.

## 단점

**운영 복잡도.** 브로커, 토픽, 파티션, 컨슈머 그룹, 오프셋 관리 등 익혀야 할 개념이 많다. 단일 노드로 시작해도 나중에 스케일아웃하려면 파티션 재분배, 복제 계수 조정 같은 작업이 필요하다. 처음 개념도를 봤을 때 "이게 우체국이야, 관제탑이야" 싶었던 기억이 있다.

**추가 인프라 비용.** 검색엔진에 바로 쓰는 구조보다 컴포넌트가 하나 늘어나서, 메모리·디스크·운영 부담이 그만큼 늘어난다.

**메시지 순서 보장의 한계.** 파티션이 여러 개면 파티션 간 순서는 보장되지 않는다(같은 파티션 안에서만 순서가 보장된다). 이 프로젝트는 파티션을 1개로 뒀기 때문에 이 문제 자체는 없지만, 대신 병렬 처리 확장성을 희생한 트레이드오프가 있다(뒤에서 다룬다).

## 우리 프로젝트에 필요했던 이유

SENTINEL-OPS는 같은 로그 스트림을 목적이 다른 세 곳(원문 검색용 OpenSearch, 집계용 ClickHouse, 상관분석 엔진)으로 동시에 흘려보내야 한다. 이 팬아웃 요구 하나만으로도 검색엔진 직결 구조보다 메시지 브로커를 두는 구조가 유리했다. 게다가 보안 로그는 "하나라도 유실되면 안 된다"는 요구가 강한데, Kafka의 보존·재처리 능력이 이 요구와 정확히 맞아떨어졌다.

## 다른 후보군과 비교

메시지 브로커로 흔히 비교되는 대안은 RabbitMQ, AWS SQS/Kinesis, Redis Streams 정도다.

**RabbitMQ**는 전통적인 메시지 큐로, 복잡한 라우팅(exchange/queue 바인딩)에 강하다. 다만 메시지를 소비하면 기본적으로 큐에서 사라지는 모델이라, "여러 소비자가 같은 메시지를 각자 독립적으로 재처리"하려면 별도 설계가 필요하다. 편지를 한 사람이 읽으면 사서함에서 아예 없어지는 구조라, 다른 부서가 같은 편지를 또 보고 싶으면 미리 복사본을 만들어놔야 한다. 대용량 스트리밍 처리량 면에서도 Kafka가 더 유리하다.

**AWS Kinesis**는 Kafka와 개념적으로 비슷한 완전관리형 스트리밍 서비스다. 운영 부담이 적다는 큰 장점이 있지만, 특정 클라우드 벤더에 종속되고 비용 구조가 사용량에 비례한다. SENTINEL-OPS는 온프레미스에 가까운 단일 VM 환경에서 직접 운영하는 걸 전제로 했기 때문에 자체 호스팅이 가능한 Kafka를 택했다.

**Redis Streams**는 이미 Redis를 상관분석 엔진의 상태 저장(카운터, 시퀀스)에 쓰고 있어서 추가 컴포넌트 없이 재사용할 수 있다는 매력이 있었다. 다만 Kafka만큼 대규모 보존·재처리·컨슈머 그룹 생태계가 성숙하지 않았고, 메모리 기반이라 대용량 로그를 장시간 보존하기에는 부담이 컸다.

결국 "다자간 팬아웃 + 긴 보존 + 재처리 + 검증된 대용량 처리"라는 조합에서 Kafka가 가장 적합했다.

## 실제 구성: 단일 노드 KRaft, 토픽별 보존 정책

실제로는 주키퍼 없이 브로커가 컨트롤러 역할까지 겸하는 KRaft 모드 단일 노드(`apache/kafka:4.3.1`)로 구성했다. 예전 방식(주키퍼 + 브로커, 두 개의 서로 다른 시스템이 손잡고 운영되는 구조)보다 관리 포인트가 하나 줄어드는 셈이다. `AUTO_CREATE_TOPICS_ENABLE=false`로 토픽 자동 생성을 꺼두고, `kafka-init`이라는 1회성 컨테이너가 브로커 헬스체크가 끝난 뒤에만 토픽을 명시적으로 만들도록 했다. Collector가 "브로커 컨테이너가 떴다"가 아니라 "토픽이 실제로 준비됐다"까지 기다리게 하기 위함이다. 문 열자마자 손님을 들이지 않고, 사서함 배치까지 끝난 다음에 문을 여는 것과 같다.

```bash
for topic in events.was events.waf events.falco events.audit events.normalized; do
  kafka-topics.sh --create --bootstrap-server kafka:9092 \
    --topic "$topic" --partitions 1 --replication-factor 1 \
    --config retention.ms=86400000 --config cleanup.policy=delete --if-not-exists
done
```

소스별 원본 토픽(`events.was` / `events.waf` / `events.falco` / `events.audit`)과 정규화된 이벤트가 모이는 `events.normalized`는 보존 기간을 24시간으로 뒀다. 처리에 실패한 이벤트가 쌓이는 `events.dlq`, `events.unknown`은 사람이 수동으로 들여다봐야 하는 대상이라 대응 시간을 벌기 위해 7일로 늘렸다.

## 트러블슈팅: 파티션 1개라는 비용의 한계

파티션과 복제는 전 토픽 모두 1개다. 단일 노드 환경에서는 복제 계수 3이 기본값인 offsets/transaction 내부 토픽을 그대로 두면 브로커가 기동조차 되지 않아 낮춰야 했고, 파티션도 1개로 뒀다.

이건 순전히 비용 문제였다. 파티션·복제 구성을 이것저것 실험해보려면 그때마다 브로커를 다른 스펙으로 띄워서 실제 처리량 차이를 재봐야 하는데, 4vCPU/16GB 단일 VM 하나로 Kafka, 세 저장소, correlation-engine, API 서버까지 전부 같이 띄우고 있는 환경에서는 이런 실험 자체가 아쉬운 조건이었다. 파티션을 늘리고 복제 노드를 추가해가며 "어느 지점부터 처리량이 늘어나는지"를 눈으로 확인하려면 VM 스펙을 계속 올려가며 테스트해야 하는데, 그때마다 실제로 비용이 들어가는 일이라 지금 트래픽 규모에서 당장 필요하지 않은 확장까지 미리 사서 검증할 이유는 없다고 판단했다.

다만 이게 카프카를 쓴 이유 자체를 무너뜨리는 건 아니다. 백프레셔 흡수, 서로 다른 컨슈머 그룹으로의 1대N 팬아웃, 재처리 가능성은 파티션 수와 무관하게 그대로 작동한다(사서함이 칸막이 하나든 여러 칸이든, 다른 부서가 각자 열쇠로 와서 확인하는 데는 지장이 없다). 파티션 1개가 실제로 막는 건 "같은 컨슈머 그룹 안에서 인스턴스를 여러 대로 늘려 병렬 처리하는" 수평 확장 한 가지뿐이다. 즉 지금 구조는 normalizer나 Data Prepper 같은 소비자를 여러 대로 늘려도 처리량이 늘지 않는다는 뜻이다. 사서함이 하나뿐이면 그 앞에 직원을 몇 명 세워둬도 결국 한 번에 한 사람만 문을 열 수 있는 것과 같다. 트래픽이 크게 늘어난다면, 그리고 그때 가서 VM을 늘릴 비용 여유가 생긴다면 가장 먼저 손봐야 할 지점이 여기다. 파티션을 늘리려면 토픽을 새로 만들거나(기존 파티션 수는 늘릴 수는 있어도 줄일 수는 없음) 컨슈머 그룹 설계를 다시 점검해야 한다.

## 다음 편 예고

Kafka에 쌓인 로그는 이제 목적이 다른 세 저장소로 흘러간다. 다음 글에서는 왜 저장소를 하나로 통일하지 않고 셋으로 나눴는지, 그리고 각 저장소가 실제로 Kafka를 어떻게 다른 방식으로 소비하는지 다룬다.
