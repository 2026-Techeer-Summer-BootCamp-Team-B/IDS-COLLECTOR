# SENTINEL-OPS 아키텍처 — 로그 한 줄이 대시보드에 뜨기까지

쿠버네티스 환경에서는 WAF·WAS·컨테이너 런타임(Falco)·K8s Audit 4개 계층에서 로그가 각각 발생한다. 문제는 이 로그를 계층별로 따로 들여다보면, 공격자가 여러 계층을 순서대로 넘나드는 연쇄적인 공격 흐름이 "4개의 무관한 해프닝"으로 파편화돼 보인다는 점이다. 개별 알람은 울리지만 전체 그림은 아무도 못 보는 상태다.

SENTINEL-OPS는 이 문제를 풀기 위해, 로그가 발생한 순간부터 대시보드에 뜨기까지 6단계 파이프라인을 거치도록 설계했다. 이 글은 그 6단계를 짧게 훑어보는 요약본이고, 각 단계마다 더 깊게 다룬 글로 링크를 걸어뒀다.

---

## 1. 로그 수집 — 왜 OpenTelemetry인가

WAF·WAS·Falco·K8s Audit 4개 소스는 포맷도, 발생 위치도, 심각도 기준도 전부 다르다. 이걸 각자 다른 방식으로 수집하면 나중에 상관분석 단계에서 포맷 맞추는 데만 상당한 비용이 든다. 그래서 수집 단계부터 OpenTelemetry(OTel)로 규격을 통일했다. OTel Collector가 `log.source` 태그 하나로 소스별 파이프라인을 자동 분기하고, 배치 타임아웃을 5000ms→500ms로 낮춰 저볼륨 구간의 반영 지연도 10분의 1로 줄였다.

**자세히 보기 →** [① 로그 수집: 왜 OpenTelemetry인가](velog-링크-넣기)

## 2. 전송 — 왜 gRPC인가

Collector까지 데이터를 실어 나르는 구간은 gRPC를 택했다. Protobuf 바이너리 직렬화와 HTTP/2 멀티플렉싱 덕분에 JSON 기반 REST보다 오버헤드가 낮고, 커넥션을 유지한 채 로그를 계속 흘려보내는 스트리밍 워크로드와도 궁합이 좋다. 보안 로그는 "얼마나 빨리 이상 징후를 포착하느냐"가 곧 대응 골든타임이라, 속도 이점이 큰 쪽을 택했다.

**자세히 보기 →** [② 전송: 왜 gRPC인가](velog-링크-넣기)

## 3. 관문 — Traefik과 mTLS

gRPC 트래픽이 클러스터 안으로 들어오기 전, Traefik이라는 단일 진입점을 거친다. 여기서 단순 토큰 인증이 아니라 mTLS(상호 TLS)로 한 단계 더 강하게 검증한다. Target 서버의 otel-collector가 클라이언트 인증서를 붙여 보내고, Traefik이 우리가 발급한 CA로 서명됐는지 확인한 뒤에만 통과시킨다. 이 구간에서 gRPC의 h2c 프리페이스를 Traefik이 HTTP/1.1로 오인해 연결이 깨지던 버그도 실제로 겪고 고쳤다.

**자세히 보기 →** [③ 관문: Traefik과 mTLS](velog-링크-넣기)

## 4. 메시지 브로커 — 왜 Kafka인가

Collector 뒤에 검색엔진을 바로 두는 대신, Kafka를 중간 버퍼로 뒀다. 트래픽 스파이크를 흡수하는 백프레셔 흡수, 같은 로그를 세 저장소로 동시에 흘려보내는 1대N 팬아웃, 장애가 나도 처음부터 다시 처리할 수 있는 재처리 가능성 — 이 세 가지가 검색엔진 직결 구조보다 유리했다. 다만 4vCPU/16GB 단일 VM이라는 비용 제약 때문에 전 토픽 파티션을 1개로 뒀고, 이게 어떤 한계로 이어지는지도 짚었다.

**자세히 보기 →** [④ 메시지 브로커: Elasticsearch 대신 Kafka를 택한 이유](velog-링크-넣기)

## 5. 저장 계층 — 세 저장소, 세 가지 역할

같은 로그라도 목적이 다르면 최적의 저장소도 다르다. 원본 로그 자유 검색은 역색인 기반의 OpenSearch, 대량 로그 집계·통계는 컬럼 지향 ClickHouse, 그리고 인시던트 상태처럼 정합성이 생명인 데이터는 ACID를 보장하는 PostgreSQL — 이렇게 세 저장소가 각자 다른 방식으로 Kafka를 소비한다. PostgreSQL은 원본 로그 사본이 아니라 상관분석 결과만 저장한다는 점이 핵심이다.

**자세히 보기 →** [⑤ 저장 계층: 세 저장소, 세 가지 역할](velog-링크-넣기)

## 6. API와 프론트엔드 — 흩어진 저장소를 하나의 화면으로

세 저장소로 나뉜 데이터는 FastAPI 서버가 요청 성격에 따라 알맞은 곳을 조회해 프론트엔드에는 그 구분이 아예 보이지 않게 만든다. KPI·통계처럼 몇 초 지연이 괜찮은 화면은 폴링을, 공격 알림처럼 즉시 반영돼야 하는 화면은 WebSocket을 쓴다. 폴링 주기도 2초 고정값에서 관리자가 0.5초~30초 사이에서 직접 고를 수 있게 바꿨다.

**자세히 보기 →** [⑥ API와 프론트엔드: 흩어진 저장소를 하나의 화면으로](velog-링크-넣기)

## 마무리

표준화된 수집(OTel) → 빠른 전송(gRPC) → 인증된 관문(Traefik/mTLS) → 안정적인 분배(Kafka) → 목적별 저장(OpenSearch/ClickHouse/PostgreSQL) → API 서빙(FastAPI)까지, 로그 한 줄이 대시보드에 뜨기까지 거치는 이 여섯 단계 각각에 "왜 이 기술을 선택했는가"와 "실제로 어떤 문제를 겪고 고쳤는가"를 담아 시리즈로 정리했다. 각 편의 자세한 이야기는 위 링크에서 이어진다.
