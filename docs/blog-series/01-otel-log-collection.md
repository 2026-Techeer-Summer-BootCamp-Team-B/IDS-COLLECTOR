# [SENTINEL-OPS 아키텍처 시리즈 ①] 로그 수집: 왜 OpenTelemetry인가

*쿠버네티스 3계층 로그를 하나의 파이프라인으로 모으는 SENTINEL-OPS 아키텍처를 단계별로 풀어본다. 이번 글은 가장 앞단인 "수집" 단계다.*

## 세 계층, 세 가지 다른 언어

쿠버네티스 환경에서 보안을 들여다보려면 최소 세 계층의 로그가 필요하다.

- **WAS**: 애플리케이션이 받은 HTTP 요청과 응답. "누가 어떤 엔드포인트를 어떤 파라미터로 호출했는가"를 보여준다.
- **Falco**: 컨테이너 런타임에서 발생하는 시스템 콜 기반 이벤트. "컨테이너 안에서 비정상적인 프로세스가 실행되거나 민감한 파일에 접근했는가"를 감시한다.
- **Kubernetes API(Audit)**: 클러스터 자체에 대한 조작 이력. "누가 어떤 권한으로 어떤 리소스를 만들거나 바꿨는가"를 기록한다.

이 셋을 한 회사의 세 직원이라고 생각해보자. WAS는 영어로 보고서를 쓰고, Falco는 독일어로 쓰고, K8s Audit는 프랑스어로 쓴다. 셋 다 유능하고 성실하지만, 이 셋의 보고서를 한 사람이 동시에 읽고 "종합해서 뭔 일이 벌어지고 있는지" 판단해야 하는 입장이라면 이야기가 달라진다. 매번 세 개의 사전을 옆에 끼고 번역기를 돌려야 한다. 소스가 하나 더 늘어난다? 통역사를 한 명 더 구해야 한다.

이걸 각자의 방식대로 수집해서 나중에 한곳에 모으려고 하면, 이후 상관분석 단계에서 "이 필드가 저 로그에서는 어떤 이름으로 불리는가"를 맞추는 데만 상당한 개발 비용이 든다.

## OpenTelemetry란 무엇인가

OpenTelemetry(OTel)는 CNCF(Cloud Native Computing Foundation)가 관리하는 오픈소스 관측성(Observability) 표준이다. 로그(Logs), 메트릭(Metrics), 트레이스(Traces) — 흔히 "관측성의 세 기둥"이라 부르는 이 세 가지 신호를 하나의 공통 데이터 모델과 하나의 전송 규격(OTLP, OpenTelemetry Protocol)으로 통일해서 다루는 게 핵심이다. 앞서 든 비유로 돌아가면, "회사 규정상 모든 보고서는 영어로 쓴다"는 사규를 만든 셈이다. 각 직원(소스 서버)은 자기 나라 말을 몰라도 되고, 그냥 규정만 지키면 된다.

구성 요소는 크게 두 가지다.

- **SDK/계측 라이브러리**: 애플리케이션 코드에 심어서 로그·메트릭·트레이스를 OTLP 규격으로 내보내게 하는 부분.
- **Collector**: SDK로부터 받은 데이터를 수신(Receive) → 가공(Process) → 내보내기(Export)하는 독립 프로세스. 수신 프로토콜, 가공 로직, 내보낼 백엔드를 모두 설정 파일로 조립할 수 있다.

SENTINEL-OPS에서는 애플리케이션 코드 안에 SDK를 직접 심는 대신, 각 서버 옆에 OTel Collector를 하나 두고 그 Collector가 로그를 표준 규격으로 재가공해서 우리 쪽 파이프라인으로 넘겨주는 구조를 쓴다. Collector는 말하자면 공항 입국 심사대 같은 존재다. 어느 나라에서 오든(어떤 소스든) 여권(로그)만 정해진 형식으로 갖고 오면, 심사대를 통과하는 순간부터는 다 같은 규칙 아래에서 움직인다.

## 장점

**벤더 중립성.** 특정 저장소나 분석 백엔드에 종속되지 않는다. Collector 설정만 바꾸면 내보내는 곳(Exporter)을 Kafka에서 다른 시스템으로 바꿀 수 있고, 계측 코드(소스 서버 쪽)는 전혀 손댈 필요가 없다. 나중에 마음이 바뀌어도 이혼(?)이 쉽다는 뜻이다.

**이기종 데이터의 통합.** 로그, 메트릭, 트레이스를 같은 데이터 모델(Resource + Attributes 구조)로 표현하기 때문에, WAS 애플리케이션 로그와 Falco의 런타임 보안 이벤트, K8s API의 감사 로그처럼 출처가 전혀 다른 데이터도 같은 파이프라인에 태울 수 있다.

**확장성.** 마이크로서비스가 늘어나 수집 대상이 늘어나도 Collector 설정만 확장하면 된다. 복잡한 쿠버네티스 환경에서도 운영 부담 없이 모니터링 범위를 넓힐 수 있다.

**생태계와 표준화.** CNCF 프로젝트로 대부분의 클라우드 벤더(AWS, GCP, Azure)와 관측성 도구(Datadog, Grafana, Elastic)가 OTLP를 기본 수신 규격으로 지원한다. 나중에 특정 SaaS로 백엔드를 옮기더라도 마이그레이션 비용이 낮다.

## 단점

**초기 러닝 커브.** Collector의 Receiver/Processor/Exporter/Connector 개념과 파이프라인 설정 문법(YAML)을 익히는 데 시간이 든다. 특히 라우팅 커넥터처럼 조건부 분기 로직은 처음 다룰 때 직관적이지 않다. 처음 YAML을 열어보면 "이게 설정 파일이야, 프로그래밍 언어야" 싶은 순간이 온다.

**Collector 자체가 장애 지점이 될 수 있다.** 모든 로그가 Collector를 거치므로, Collector가 죽으면 그 뒤로는 로그가 아예 들어오지 않는다. 공항 입국 심사대가 마비되면 비행기가 아무리 많이 도착해도 아무도 나라 안으로 못 들어오는 것과 같다. 그래서 Collector의 메모리 사용량을 제한하는 `memory_limiter` 프로세서, 배치 크기를 관리하는 `batch` 프로세서 같은 안전장치를 반드시 같이 구성해야 한다.

**오버엔지니어링 위험.** 소스가 1~2개뿐인 소규모 프로젝트에는 OTel의 표준화 이점보다 설정 복잡도가 더 크게 느껴질 수 있다. 소스가 여러 개고 계속 늘어날 가능성이 있을 때 이점이 커지는 도구다.

## 우리 프로젝트에 필요했던 이유

SENTINEL-OPS는 정확히 OTel이 유리해지는 조건에 해당했다. 소스가 WAS/WAF/Falco/K8s Audit 4개로 이미 이질적이었고, 앞으로 소스가 더 늘어날 가능성(예: 다른 클러스터, 다른 서비스)도 열려 있었다. 각 소스를 따로 수집해서 나중에 상관분석 엔진 앞에서 포맷을 맞추는 방식이었다면, 소스가 하나 늘어날 때마다 파서를 새로 짜야 했을 것이다.

또한 OTel Collector에는 `routing` 커넥터가 기본 제공되어, `resource.attributes["log.source"]` 같은 태그 하나만으로 소스별 파이프라인 분기를 코드 한 줄 없이 설정만으로 구현할 수 있었다. 이 덕분에 정규화(normalizer) 이전 단계에서부터 이미 소스가 깔끔하게 분리된 상태로 Kafka에 적재된다.

## 다른 후보군과 비교

로그 수집기로 흔히 비교되는 대안은 Fluentd/Fluent Bit, Logstash, Filebeat 정도다.

**Fluentd / Fluent Bit**는 로그 수집에 특화되어 있고 가볍다는 장점이 있지만, 메트릭·트레이스까지 같은 파이프라인에 태우려면 별도 도구를 추가로 연동해야 한다. 로그만 다룬다면 충분히 좋은 선택지지만, SENTINEL-OPS는 향후 메트릭·트레이스 기반 관측성까지 같은 파이프라인으로 확장할 가능성을 열어두고 싶었다.

**Logstash**는 강력한 변환(그록 파싱 등) 기능을 갖췄지만 JVM 기반이라 리소스 사용량이 상대적으로 무겁고, ELK 스택에 종속적인 성격이 강하다. 저장소를 OpenSearch/ClickHouse/PostgreSQL로 나눠 쓰는 구조와는 결합이 헐거워진다.

**Filebeat**는 파일 기반 로그 수집(tail)에 최적화되어 있는데, SENTINEL-OPS는 파일을 직접 tail하기보다 애플리케이션·런타임에서 이벤트를 능동적으로 내보내는(push) 구조를 원했다.

결국 "로그·메트릭·트레이스를 같은 표준으로, 벤더 중립적으로, 소스가 늘어나도 설정만으로 확장 가능하게" 다루고 싶다는 요구에 가장 잘 맞는 게 OpenTelemetry였다.

## 실제 구현: 태그 기반 라우팅

실제 Collector 설정(`otel-config.yaml`)에서는 OTLP 리시버가 로그를 받으면, `resource.attributes["log.source"]`라는 태그(was / waf / falco / k8s-audit) 하나만 보고 곧바로 소스별 파이프라인으로 라우팅한다.

```yaml
connectors:
  routing/by-source:
    default_pipelines: [logs/unknown]
    error_mode: ignore
    table:
      - statement: route() where resource.attributes["log.source"] == "was"
        pipelines: [logs/was]
      - statement: route() where resource.attributes["log.source"] == "waf"
        pipelines: [logs/waf]
      - statement: route() where resource.attributes["log.source"] == "falco"
        pipelines: [logs/falco]
      - statement: route() where resource.attributes["log.source"] == "k8s-audit"
        pipelines: [logs/audit]
```

이 라우팅 커넥터는 말하자면 우체국의 우편물 분류 로봇이다. 소포에 붙은 라벨(태그) 하나만 스캔해서 컨베이어 벨트를 어느 방향으로 보낼지 결정한다. 여기서 눈여겨볼 부분은 `default_pipelines: [logs/unknown]`이다. 태그가 없거나 인식되지 않는 값이면 `events.unknown`이라는 별도 경로로 보내도록 해뒀다. 라벨 없는 소포를 그냥 아무 데나 던져버리지 않고 "라벨 없음" 창구에 따로 모아두는 것과 같다. 태깅이 누락된 이벤트를 조용히 흘려버리지 않고, 눈에 띄게 만들어서 나중에 원인을 바로 찾을 수 있게 하기 위함이다.

## 트러블슈팅: 원문 로그가 컨테이너 stdout에 쌓이던 문제

Collector 설정에는 원래 `debug` exporter(verbosity: detailed)를 4개 정상 파이프라인(logs/was, logs/waf, logs/falco, logs/audit)에도 걸어뒀다. 개발 중에는 파이프라인이 제대로 도는지 바로 눈으로 확인할 수 있어서 편리했기 때문이다. 마치 공사 현장에 CCTV를 곳곳에 설치해두고 "잘 돌아가나" 확인하는 느낌이었달까.

문제는 이걸 그대로 운영 환경까지 가져가면서 발생했다. `debug` exporter가 상시로 켜져 있으니 이벤트 원문(WAS 쿼리스트링, WAF 페이로드 스니펫 등 자격증명·공격 페이로드가 섞일 수 있는 필드)이 컨테이너 stdout에 계속 쌓였고, 당시엔 Docker 로그 로테이션 설정도 없던 상태라 디스크가 누적되는 문제로 이어졌다. 공사가 끝났는데도 CCTV를 계속 켜두고 녹화 파일을 하나도 안 지운 셈이다. 감사 과정에서 이 조합이 디스크 누적의 가장 큰 기여 요인으로 지목됐다.

수정은 두 갈래로 했다. 먼저 4개 정상 파이프라인에서는 `debug` exporter를 뺐다. 대신 태깅이 누락된 안전망 경로(`logs/unknown`)에만 `debug` exporter를 예외적으로 남겨서, 정상 상태에서는 깊이가 0이어야 할 이 경로에 뭔가 들어오면 바로 원문을 확인할 수 있게 했다. 그리고 별도로 모든 컨테이너에 `json-file` 로그 드라이버 기반 로테이션(`max-size: 50m, max-file: 3`)을 추가해서, 혹시 다른 경로로 로그가 쌓이더라도 디스크를 무한정 잡아먹지 않도록 안전장치를 이중으로 뒀다.

## 트러블슈팅: 배치 타임아웃 튜닝 — 응답 시간을 줄인 이야기

Collector의 `batch` 프로세서는 이벤트를 일정 시간(또는 개수)만큼 묶어서 한 번에 Kafka로 내보낸다. 마치 택배 기사가 한 집 한 집 배달하는 대신, 트럭에 물건을 어느 정도 채운 다음 한 번에 나가는 것과 비슷하다. 효율은 좋지만, 트럭이 가득 찰 때까지 마냥 기다리면 먼저 실린 택배는 하염없이 대기해야 한다.

처음에는 이 타임아웃을 5초로 잡았다. 트래픽이 많을 때는 문제가 없지만(트럭이 금방 차니까), 데모나 테스트처럼 이벤트가 뜨문뜨문 들어오는 저볼륨 상황에서는 이 5초가 그대로 "로그가 발생한 시점부터 대시보드에 반영되기까지의 지연(E2E 레이턴시)"에 더해졌다. 공격 하나를 일으키고 화면에 뜰 때까지 5초 넘게 기다려야 한다면, 시연이든 실사용이든 답답하게 느껴진다. 트럭 한 대 채우자고 택배 하나를 5초씩 묵혀두는 셈이니까.

1차로 1초까지 낮췄고, 이후 재점검하면서 500ms까지 더 낮췄다(`send_batch_size: 8192`는 유지 — 트래픽이 많을 때는 시간보다 이 개수 기준으로 먼저 플러시되므로 저볼륨 구간의 지연만 줄이는 효과다). 물론 배치 타임아웃을 무작정 낮추면 배치가 작아져 Kafka로 나가는 요청 수 자체가 늘어나는 트레이드오프가 있다. 트럭을 자주 보낼수록 기름값(요청 오버헤드)이 더 든다. 지금 트래픽 규모에서는 이 정도가 체감 지연과 처리 비용 사이의 합리적인 지점이었다.
